## 0. Обязательное решение владельца продукта

В NoSale ровно **два независимых режима**:
- **Стандартная защита (Standard)** — существующее и работающее поведение: продавец задаёт максимальную скидку в процентах, NoSale отслеживает превышение и корректирует только документированное поле **скидки продавца** через WB API с существующими проверками, настройками, журналом, подтверждением изменений. **НЕ ПЕРЕПИСЫВАТЬ / НЕ ЛОМАТЬ / НЕ ТИХО МИГРИРОВАТЬ**. Сохранить совместимость всех существующих записей и правил, включая текущий default=0 и дополнительное подтверждение рискованного применения 0%, до отдельно утверждённого UX изменения. Не позиционировать как механизм остановки всех видов акций.
- **Интеллектуальная защита (Smart)** — новый явно выбираемый режим, анализ реальных источников финансирования акций, расчёт продавец-оплачиваемого снижения доходности, предупреждение и применение технически разрешённой защиты только к убыточным/нарушающим лимиты случаям. Не уменьшать полезные платформенные скидки. Работа AI опциональная: отказ LLM не отключает защитные алгоритмы.

## 1. Продуктовая логика

На уровне **каждого магазина** (в перспективе группы товаров/SKU):
- `mode = standard | smart` (дефолт для существующих аккаунтов = `standard`, без изменения текущего алгоритма).
- **Standard**: вызывается неизменённый существующий `monitor.check_account`/вынесенный без изменения семантики StandardPolicy.
- **Smart**: отдельная реализация SmartPolicy, единственный определённый общий компонент — низкоуровневый WBClient, журнал, лимитирование, безопасная отправка и подтверждение изменений.
- Одновременно не исполнять две политики на одном аккаунте: единая активная политика, optimistic locking (`rules_version`), проверка до API write; переключение не имеет права протащить старые queued actions.
- Наблюдение/история без ограничений политики; Smart (без минимальной цены/расходов/fallback) — только `monitor_only`, без автоизменений.
- Предустановленное правило безопасности Smart: **не считать неизвестный источник скидки безвредным**.

### Классификация события в Smart

Каждый `promotion_effect` получает `funding = wb_funded | seller_funded | mixed | unknown`, `confidence`, `source_evidence`, время сбора, `data_freshness`, версии условий/расчёта.

Решение является **правилом, а не оценкой LLM**:
1. **Preserve** — *только подтверждённый WB-funded эффект* без падения розничной цены продавца и без дополнительных обязательств продавца; учесть ценовой floor и известные комиссии. Скидка покупателю может отличаться от выплаты продавцу.
2. **Correct** — seller-funded компонент нарушает заданный экономический лимит или процентный fallback, и официальное API реально позволяет соответствующую правку. Коррекция не должна отменять оплачиваемую WB часть; не предпринимать действий с неподтверждёнными акциями или правами.
3. **Uncertain** — источник, стоимость, действующие условия акции, seller payout или доступный способ контроля не подтверждены. Нельзя классифицировать как безопасное. При заранее включённом **консервативном процентном fallback** применять Standard лимит **исключительно к той же скидке продавца**, которую Standard и сейчас умеет менять; остальные механики — `needs_attention` с оперативным уведомлением и инструкцией. Не обещать автоматическую отмену того, для чего WB не дал официальный метод.

Важно: заявленное `confidence=0.99` от AI **не равно финансовой гарантии**. Признак `safe` требует проверяемых фактов, а не вероятностного процента.

### Рекомендуемые поля Smart по товару

- `min_seller_net_price_rub` (нижняя розничная цена с продавец-оплачиваемыми скидками) и/или `min_contribution_margin_rub`, `min_contribution_margin_percent`;
- `cogs` (себестоимость), логистика, эквайринг, комиссия, предполагаемый возврат, бонусы/кешбэк/софинансирование, налоги — каждый расход с источником, единицей, временем и уровнем определённости;
- `strict_discount_fallback_percent` (отдельная осознанная настройка; можно переиспользовать уже заданный Standard предел, но запросить подтверждение);
- `auto_correction_enabled=false` default, явное согласие и выбор товаров/категорий; `notify_enabled`, escalation preferences;
- результаты: `estimated_seller_payout`, `estimated_margin`, `actual_seller_payout` по фин.отчёту, `risk_class`, `actionability`, `coverage_status`.

Не считать прибыль и убыточность **с высокой точностью**, если в расчёте не хватает себестоимости или сопутствующих расходов. Если пользователь не ввёл затрат, применять только чёткую границу цены/процента и показывать `margin_unavailable`.

## 2. Источники данных

**Прямые источники:** WB Prices/Discounts, Content, календарь акций, финансовая детализация (`Финансы`; отдельная минимальная категория прав с согласия). Применение спецмеханик — только через официально документированные WB API endpoints. Данные могут отставать от реальных покупок: не считать недельную детализацию мгновенной.

**Слои аналитики:** моментальный snapshot цены и скидки; изменения promo ID и условий; расчёт unit economics; последующая сверка расчёта с фактическими `К перечислению` и удержаниями. Отдельно считать покупательскую цену и цену продавца; не смешивать платформенную скидку WB с WB Club discount, seller promotions, бонусными программами, промокодами продавца.

**Ограничения WB:** минимальные цены/блокировки WB работают **только для автоакций**; официальная инструкция подтверждает, что ручное добавление товара в уже идущую автоакцию способно обойти ограничения именно для выбранной акции. `nomenclatures` календаря акций не подходит для автоакций. Не изображать это как 100%-ную автоматизацию. Учитывать `rate limit`, задержки и технически недоступные методы.

## 3. Роль AI и кэширование

**LLM никогда не отправляет write requests в WB**, не устанавливает цену/скидку и не отменяет ограничение:
- AI получает санитизированный snapshot правил акции, sku, агрегированные изменения, рассчитанные метрики, анонимизированную историю, публичные условия.
- AI возвращает строго валидируемый JSON: `assessment`, `rationale`, `uncertainties`, `evidence_refs`, `suggested_next_checks`, `model_name`, `prompt_version`, `generated_at`.
- AI может извлекать условия из текстов, маркировать неоднозначные программы, объяснять человеку разницу источников финансирования, формировать отчёты и ставить вопросы к источникам.
- Инварианты принимают backend rule engine + подтверждённые данные, не мнение модели. Model confidence — вспомогательный показатель; ошибочные/hallucinated ссылки не должны становиться `verified`.
- Сервис поддерживает выбор провайдера через интерфейс (`DeepSeek/OpenRouter/Llama/другой OpenAI-compatible`), флаги вызовов, лимиты затрат, очередь, таймауты; сбой/отключение AI = deterministic protection работает как прежде.
- **Кэширование:** хранить структурированные WB факты отдельно от ответов модели; ключ AI-кэша = account/seller-safe fingerprint (promotion ID, версионированные параметры/условия, seller price, cost/rule revision, snapshot timestamp, prompt+model version, tenant ID). Кэш не используется для решения о live write без повторной проверки свежести условий/данных. Invalidate при любом изменении кампании, цены, правила, видимой информации, при истечении TTL или смене модели. Запретить межмагазинные утечки и отправку API токенов/PII в LLM.
- Вызов LLM только для нового/изменившегося или неразрешённого события, не по расписанию на каждый SKU; простые случаи закрываются правилами и кэшем.

## 4. Пользовательский интерфейс и ответственность

Страница настройки: переключатель `Стандартная защита` / `Интеллектуальная защита (beta)`. При активации Smart объяснить требования: минимальная маржа или цена, настраиваемый fallback, отдельный токен категории «Финансы» **только если используется сверка**, разрешение на чтение и осознанное включение автоматических изменений.

В UI **не писать «защищено», если WB механика не управляется по API**, данные устарели, нет расходов или стоит read-only токен. Раздельно показывать:
- `Мониторинг подключён`
- `Экономика рассчитана`
- `Автоматическая защита возможна`
- `Отправлено в WB`
- `Подтверждено WB`
- `Невозможно остановить автоматически`

По каждому товару: источник финансирования, доказательства, версия условий, плановая/текущая цена продавца, скидка покупателю, расчётная и фактическая прибыль, риск, действие, время последней синхронизации, расхождения и история. При неизвестной механике: явно и срочно сообщать «Требуется действие в кабинете WB» + переход к инструкции без притворного статуса успеха.

**Оферта/условия сервиса**: отдельно описывать механику Standard/Smart, зависимость от API WB и задержек отчётов, нет гарантий отсутствия любых убытков, неполноту классификации, обязанность продавца проверить расходы, временные ограничения и способы уведомления, журнал событий, границы полномочий автоматизации. Формулировки согласовать с юристом; оферта не заменяет техническую защиту и не освобождает от любой ответственности.

## 5. Верификация качества, до активации auto

Определить размеченный датасет **реальных, проверенных** акций + движения seller payout:
- минимум категории WB-funded, seller-funded, mixed, unknown; обычные/автоакции; WB Клуб, WB Кошелёк, seller coupons, кешбэк/баллы и софинансирование;
- случаи одновременных скидок, изменения условий между анализом и write, late financial settlement, 429, истёкший token, rate-limit, missing/freshness, WB autoaction override, ручное включение в автоакцию, API недоступно, fallback 0, switch Standard↔Smart with pending uploads;
- **первая метрика качества — false negative rate по реальному денежному риску** (сколько seller-funded убыточных событий ошибочно попали в `safe` и какой суммарный потенциальный убыток), отдельно false positive rate (потерянная возможность полезной акции).
- Целевой показатель вроде «95%/99%» не писать, пока не получена репрезентативная валидация с контрпримерами; нельзя обещать 100% безопасность без возможности контролировать все механики.
- Внедрение: (1) read-only мониторинг, (2) shadow режим Smart параллельно **без права записывать** и сопоставление с Standard, (3) обкатка через тесты на разрешённом продавце и явное подтверждение, (4) условно включаемое безопасное auto, (5) постоянный аудит actual vs predicted.

## 6. Последовательность реализации (следующие отдельные задачи)

1. Нетронутая Standard policy + регрессионный контракт тестами; SQL миграция `protection_mode` с дефолтом `standard`, 0%/existing records unchanged. Изолировать routing политики, lock/queue.
2. Read-only нормализаторы WB Campaign + Finance, хранение evidence, недостающие/устаревшие поля.
3. Smart экономика + статус неизвестности + fallback; тесты fail-safe, консистентность и идемпотентность.
4. AI провайдер + кэширование + JSON schema; AI никогда не управляет WB-write.
5. UI сравнение режимов, предупреждения, история/связанные доказательства.
6. Отдельная проверка оферты и acceptance, shadow тест на собственных данных продавца, только после этого запуск auto.
