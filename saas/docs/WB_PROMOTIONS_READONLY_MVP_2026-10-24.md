# NoSale — read-only контроль акций WB (первый вертикальный срез)

**Дата:** 2026-10-24. **Статус:** реализованный кандидат до PR/main приёмки. **Не коммерческий GO.**

## Основания и выбор архитектуры

Изучены репозитории:
- https://github.com/DeviceIngineering/wb-mcp-server — полезные отдельные сценарии календаря, аудита акций, диагностики токенов. Весь сервер и операции `wb_promotion_exit`/управления ценой **не заимствуются**. Указание «выйти» через цену — не официальный выход из автоакции, может вызвать убыток.
- https://github.com/ilyautov/marketplaces-mcp-ru — полезны schema-driven API-каталог, разделение read/write/destructive, пагинация и осторожность с токенами. Его HTTP-режим без своей авторизации непригоден для общего SaaS.
- Существующий `saas/docs/WB_PROMOTIONS_FUTURE_RESEARCH.md` — анализ юридической/экономической стороны акций.

**Решение:** собственный изолированный `WBClient` и Django-модуль. MCP и LLM не нужны для плановой проверки. Сторонние исходники не импортировались и не копировались. Никаких открытых MCP-портов или дополнительных хранилищ WB-токенов.

Официальная документация WB (текущая категория Promo Calendar):
https://dev.wildberries.ru/docs/openapi/promotion
- GET `/api/v1/calendar/promotions` — календарь; `startDateTime`, `endDateTime`, `allPromo`, `limit`, `offset`.
- GET `/api/v1/calendar/promotions/nomenclatures` — только обычные акции, `inAction=true`; **не поддерживается для автоакций**.
- Token category `Цены и скидки`; сервисный/персональный токен разделяет общий лимит методов календаря; базовый без секрета — ~1 вызов/час.
- Никаких вызовов `/upload`, изменения seller-discount, исключений или обхода частных API.

## Реализация

1. `GET /promotions/`: только кэшированные данные своего магазина, без WB I/O. Требуется действующий тарифный доступ.
2. `POST /promotions/` (`action=refresh`): CSRF, token decrypt только на сервере, проверка scope, включённой WB-сети и активного тарифа. В публичном E5 `SAAS_WB_NETWORK_ENABLED=0` — обновление **запрещено**.
3. Базовый токен: один запрос календаря, cooldown 65 минут. Сервисный/персональный: до 1 календаря + 3 запросов состава обычных акций, cooldown 15 минут. Не более 40 акций и 100 товаров для каждого изученного ID, результат маркирован как частичный. DB lock не допускает дублирующий ручной refresh.
4. Наблюдения одного магазина сохраняются в `PromotionSnapshot` (migration `guard.0013`), хранят только короткую нормализованную сводку; без токенов, сырого ответа WB и произвольных payload. При ошибке сохраняем предыдущую проверку.
5. Доступные признаки: `type=auto/regular/unknown`, название, календарь, `price/planPrice` участвующих товаров из обычных акций, сравнение цены. При `planPrice < price` — **возможное снижение цены продавца**, не установленный убыток; финансовый источник всегда `unknown`.
6. На автоакциях **не пытаемся читать недоступный список товаров**. Текущее состояние цены проверяет уже существующий WB Guard, но этот новый модуль никогда не инициирует изменения.
7. Навигация `Акции WB` и страница с предупреждением об источниках и частичности проверки.

## Приёмочные границы

**Подтверждено кодом/тестами:** HTTP GET-only, tenant isolation, тариф/CSRF, отсутствие WB вызовов по GET, обязательный token scope, cooldown, ограниченные страницы, сохранение кэша при 429, отсутствие финансовых выводов, совместимость с read-only preview.

**Ещё требуется:** авторизованный продавец с валидным токеном нужной категории для live API/schema acceptance, проверка реальных `nomenclatures` и расхождений WB response; финансовые отчёты со специальным opt-in scope, себестоимость/логистика, статус платформенной скидки, устойчивая unit economy, бизнес-правила, автоматические действия *только после* явно заданных безопасных инвариантов. Не считать это доказанной защитой от всех автоакций.

**Следующая задача:** R5.1 Finance API read-only отдельно и проверка продавцом источника выплаты; автоизменение цены из этого модуля сейчас **запрещено**.
