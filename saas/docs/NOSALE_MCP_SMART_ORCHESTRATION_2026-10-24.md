# NoSale Smart → собственный внутренний MCP — инструментальный контур R2

Дата: 2026-10-24. Изменение связано с GitHub issue #35.

## Что реализовано

- NoSale остаётся **одним MCP-сервером** с раздельными WB/Ozon адаптерами. AI Platform — только LLM/модель, а не внешний держатель WB токенов.
- Smart (Django backend) предоставляет модели **не больше 4** собственных инструментов WB или единственный placeholder Ozon. Спецификации — стандартное OpenAI chat-completions `tools` с `tool_choice=auto`, `parallel_tool_calls=false`.
- Когда модель выбирает инструмент, NoSale **проверяет имя и строгие пределы аргументов**, сам выдаёт **на 90 секунд** подписанный bearer для уже выбранного пользовательской сессией магазина, сам соединяется по **внутренней Docker-сети `http://mcp:8099/mcp`**, получает только сохранённую ограниченную информацию из NoSale. Модель никогда не получает bearer, адрес MCP, произвольный accountId, WB токен или чужую информацию.
- Не более **одного MCP-инструмента и двух AI-модельных запросов** на пользовательский вопрос; никакой рекурсии, фоновой работы, вызовов write-tools или подключения к WB API внутри MCP. Ограничения пагинации и размера контекста действуют независимо в серверном MCP и в Smart.
- Сначала действующая серверная проверка подписки Smart, дневной квоты и **двойной бюджетной резервации** на потенциальные два completion; затем запросы только через подключённый, разрешённый и верифицированный AI Platform проект. Сохранённые расходы — консервативная резервация, не официальный счет провайдера.
- Прежде чем предоставить модели расширенные сведения о товарах/акциях, продавец должен **отдельно** выбрать `mcp_consent=yes`, кроме обязательного `ai_consent=yes`. Без дополнительного согласия старое краткое AI-объяснение остаётся неизменным.
- Текстовые результаты MCP — **данные, а не инструкции**. Ответы с неподтверждёнными финансовыми утверждениями и числовыми фактами отбрасываются; недоступность MCP, отсутствие поддерживаемого tool-calling, ошибка модели или истёкший лимит приводит к старому Basic, а не к запросу новой платформы/тайному обходу лимитов.
- Во время AI-запроса подписка может истечь или быть отозвана. Проверяется до выдачи MCP-токена, на каждом вызове инструмента, после него и перед сохранением сообщения. Отозванная подписка не разрешает сохранять ответ.
- Никаких обновлений акций, скидок, цен, финансовых результатов, токенов, тарифов или владельца через MCP.

## Сети и зависимости

`saas/Dockerfile` включает SDK-клиент и модуль `nosale_mcp`. В `web` **не** запускается MCP-сервер; отдельные `mcp` контейнеры из PR #34 сохраняются без публичного порта. Путь в MCP фиксирован, перенаправления и прокси выключены. Формат — SDK v2 Streamable HTTP с реальным рукопожатием.

## Границы готовности

**Код и тесты (проверять):** контракт tool calling, валидация JSON-аргументов, tenant isolation, согласие, ограничение контекста, контроль бюджета, отклонённые подписи/права, реальный MCP протокол, PostgreSQL регрессии, публичный staging и legacy health.

**Ограничения:** владелец NoSale ещё не настроил отдельный проект NoSale на AI Platform и опубликованную модель с проверенным `tools/function calling` (AI Platform #47 и NoSale #10/#11). Поэтому live end-to-end **модельного** ответа без ключа и расходов нельзя считать пройденным. На staging AI по-прежнему OFF, а WB сеть и merchant OFF. Запрещено переиспользовать сервисные токены других проектов.

## Приёмка живого Smart

1. Верифицировать отдельный NoSale AI Platform project key, token, chat/tool-compatible model, его бюджеты/список инструментов и цену; не копировать ключи в Git.
2. Войти подтверждённым владельцем, включить AI через owner admin, проверить верифицированный каталог и ограниченный budget.
3. На разрешённом фиктивном WB-магазине с согласиями проверить Smart → function call → внутренний MCP → grounded answer. Проверить missing consent, expired grant, token rotation, отказ внешним хостам.
4. Тестировать настоящий WB seller token / Finance и merchant только после отдельной авторизации R5. Legacy продавец изолирован.
