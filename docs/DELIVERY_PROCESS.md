# NoSale — инженерный цикл и приёмка

Это дополнение к [AI Platform / process](https://github.com/Anderhaos/ai-platform/blob/main/policies/process.md), а не копия или замена общих правил. Актуальные нормы: [infra-operations](https://github.com/Anderhaos/ai-platform/blob/main/policies/infra-operations.md), [task-integration](https://github.com/Anderhaos/ai-platform/blob/main/policies/task-integration.md), [execution-contracts](https://github.com/Anderhaos/ai-platform/blob/main/policies/execution-contracts.md), [CI](https://github.com/Anderhaos/ai-platform/blob/main/policies/ci.md), [testing](https://github.com/Anderhaos/ai-platform/blob/main/policies/testing.md), [deploy](https://github.com/Anderhaos/ai-platform/blob/main/policies/deploy.md).

## Границы продукта

- Основной SaaS находится в `saas/`: `guard/` (WB, товары, акции, защитные правила), `portal/` (кабинет и авторизация), `billing/` (доступ), `push/` (уведомления), `e2e/`. Корневой `app/` — старый отдельный прототип, не источник SaaS-функций.
- Данные, права, токены, уведомления и операции изолируются по пользователю **и выбранному магазину**. Никакого чтения или записи в чужом магазине.
- Презентационная задача не меняет worker, лимиты защиты, API-токены или платежи без самостоятельного AC и соответствующей оценки риска.
- Интеграция площадки показывается только когда реальные API, авторизация и товары поддержаны; нельзя под видом Ozon выводить данные WB. Неизвестные расходы, финансирование акций и маржа не выдаются за достоверные.
- Продукционные токены, WB-цены и данные продавцов не используются как тестовые фикстуры. Частота read-only WB-запросов соблюдает официальный API; запись требует отдельно утверждённой продуктовой логики.

## Один законченный блок до CI

1. **Восстановить состояние**: выяснить текущие GitHub Issue/PR и полный DoD, посмотреть актуальный remote `main`, ветки и продуктовые границы. Существующую незавершённую задачу продолжать в её ветке, не создавать дубль.
2. **Собрать цельный срез**: связанная серверная логика, интерфейс, адаптив, тесты, документация и необходимые границы безопасности реализуются вместе. Одна задача — одна ветка от свежего remote `main`, один PR. Нельзя объявить задачу выполненной по одному вспомогательному коммиту.
3. **Точечная проверка**: каждый критерий AC сопоставить с unit / integration / Chromium / runtime. Во время реализации — целевые быстрые проверки; после завершения среза — установленный для этой области CI. Не запускать дорогой CI на каждом мелком изменении.
4. **PR и CI**: изменения `saas/**` проверяются существующим `.github/workflows/mpnosale-saas.yml` (работы `django-tests`, `postgres-tests`, `browser-e2e`). Проверить все необходимые green-checks именно для **финального PR HEAD SHA**, а не раннего коммита. Не запускать ручные циклы polling; использовать детерминированную ограниченную проверку или итоговый receipt.
5. **Review и merge**: независимая приёмка обязательна там, где этого требует риск/контракт; положительный CI не выдаётся за независимый review. После применимых gates — разрешённый merge, затем проверить, что SHA merge достижим из актуального remote `main`. Если review или CI недоступны, назвать конкретный `INTEGRATION_BLOCKED`, а не `DONE`.
6. **Отдельный release**: штатный подтверждённый deploy-путь, ожидаемый SHA, возможность отката, один post-deploy smoke и runtime evidence. Production checkout — чистое зеркало уже принятого исходного кода, **не** место для правок. `saas/README.md` и `PORTAL_DEPLOY.md` содержат исторические описания E4/E5/staging; их команды не являются автоматически подтверждённым путём для `nosale.pro`. Если release path не подтверждён — `DEPLOY_BLOCKED`, без ручного hotpatch.
7. **CLOSED**: полный DoD, включая реальный runtime, если он изменён, подтверждён. Отчёт должен различать implemented / verified / merged / deployed / remaining AC. Не засчитывать незавершённое за готовое.

## Инструменты и шум

- Исходники редактируются Git/GitHub или нормальным локальным checkout с Git. Desktop Commander используется **только по необходимости состояния конкретного хоста**: Docker, сервисы, штатный deploy, логи и health. Не переносить каждую правку с помощью десятков GitHub-blob-вызовов и не разрабатывать в production checkout.
- Для повторяемых действий использовать имеющиеся сценарии проекта и `scripts/agent-toolbox` AI Platform, где применимо. Не создавать каждый раз новый одноразовый скрипт как замену каноническому пути.
- Одна крупная реализация → целевая проверка → финальный CI → review → merge → release. Не повторять полный тест только ради ожидания и не опрашивать Actions каждые секунды.
- Передавать пользователю завершённые результаты или реальные решения/блокеры, а не длинную ленту микроопераций.

## Приёмка отдельных типов задач

- **Навигация/адаптив**: одинаковые контейнеры страниц, отсутствие горизонтальной прокрутки, рабочие состояния Desktop и Mobile, отсутствие ложных действий и дублирующих разделов.
- **Защита скидок**: разделять намерение отправки и реально подтверждённое WB-исправление; проверить лимиты, изоляцию, worker и регрессию действующего магазина.
- **Акции**: отделять календарь от подтверждённого участия магазина и состава артикулов; автоакции не приписывать конкретным товарам без подтверждения; неизвестное финансирование и себестоимость не считать выгодой; rate-limit и read-only обязательны.
- **Подписка/доступ/почта**: отдельные tenant/auth/billing проверки; UX-упрощение не открывает доступ без положительного grant.

Документальная правка вне `saas/**` **не требует повторного Django/PostgreSQL/Chromium CI только из-за добавления этого файла**, если другие правила/ветка не требуют его. Проверка достаточна по диффу документации и интеграции в `main`.
